# Skill / Knowledge 机制与流程图

> 覆盖：资源配置（gateway `skill:` 块 / Knowledge 服务配置）、触发链路、以及各自 LLM 调用的数据流。
> 代码根：`MemoryCore/src/core/skill/`、`MemoryCore/src/gateway/skill-handlers.ts`、`MemoryKnowledge/src/`、`MemoryProxy/src/{skill,knowledge,injection}/`。

---

## 1. Skill 机制

### 1.1 资产模型

- Skill = 一个类级别的可复用 **SKILL.md**（能力说明书）+ 可选的 `files/` 支撑文件（脚本/SQL/模板）。
- 库存储：`core/skill/skill-store.ts`（SQLite），带版本化（`skill-versioning.ts`）与权限（`skill-permission.ts`）。
- 资源定位（routing）：`routing.mode: bm25`，`searchTopK: 20` —— 注入时按会话内容检索相关 skill。

### 1.2 配置块（memory-core gateway YAML 的 `skill:`）

```yaml
skill:
  enabled: true
  routing: { mode: bm25, searchTopK: 20 }
  extraction:
    enabled: true
    maxIterations: 16        # Skill Review Agent 工具循环最大轮数
    maxTokens: ...           # review 单次 LLM 输出 token 上限（独立于 llm.maxTokens）
    headChars / tailChars: … # 归档切片 head/tail 截断
  queue: { backend: local, ... }   # 异步抽取队列
  resources: { maxResourceSizeBytes: 5000000 }
```

### 1.3 触发链路（两条路径）

```text
┌─ 异步归档 ─────────────────────────────────────────────────────────┐
│ POST /v3/skill/conversation/add（proxy skill-bridge 转调）          │
│   → message-compressor（压缩）/ oversize-strategy / prepare-archive │
│   → 入队 queue（local, 按 instance 隔离）                            │
│   → skill-core-sink 消费 → SkillExtractor（Skill Review Agent）      │
└─────────────────────────────────────────────────────────────────────┘

┌─ 同步直触发 ──────────────────────────────┐
│ POST /v3/skill/extract（direct-trigger）   │
│   → buildSkillExtractorForInstance(...)   │
│   → SkillExtractor 同步跑一轮 review       │
└────────────────────────────────────────────┘
```

### 1.4 Skill Review Agent 的 LLM 数据流（唯一的 skill LLM 调用）

```text
SkillExtractor.extract(recentBlock, truncated)
  │  user prompt = [hint 可选] + 会话切片(截断) + <<end-of-transcript>> 锚点
  ▼
StandaloneLLMRunner.run({ systemPrompt: SKILL_REVIEW_PROMPT, prompt, ... })
  │  @ai-sdk/openai 兼容调用（baseUrl/apiKey/model ← 内核 llm 配置块）
  ▼
AI SDK 工具循环（最多 maxIterations 轮）：
  skill_list / skill_view（读）
  skill_create / skill_update / skill_patch / skill_files_write（写，expected_version 乐观锁）
  ▼
结束 = 一句摘要行（audit 日志用），所有变更经工具持久化
```

> `skill-listing-prompt.ts`（`<available_skills>` 的 header/footer + `SKILLS_GUIDANCE`）是**纯静态注入文本，不调用 LLM**。

### 1.5 Proxy 注入面（Agent 可见，无 LLM）

- `SkillInjector` → `<available_skills>` 块（session_init 时机注入，类似 skill listing）
- `SkillToolsInjector` → `<skill_tools>` 块（Bash curl 走 proxy 的 skill bridge）
- `skill/core-client.ts` → 调内核 `/v3/skill/*`
- `asset-reflection`（可选）→ 让 LLM 反思资产命中质量

## 2. Knowledge 机制

### 2.1 资产模型

- **wiki 资产**：源文件（markdown 等）→ `ingest-v2` 管线 → 页面化 wiki（YAML frontmatter + wikilink 交叉引用）。
- **code-graph 资产**：`engines/code` 结构索引（`indexProject` / `openIndex` / `syncIndex`），**全程无 LLM**。
- 服务形态：`MemoryKnowledge`（独立进程，默认端口 8421，API 前缀 `/v3`）。

### 2.2 配置（环境变量，`MemoryKnowledge/src/config.ts`）

| 环境变量 | 默认 | 含义 |
|---|---|---|
| `LLM_MODE` | `proxy` | 全局默认路由；`custom` = BYO 直连 |
| `LLM_PROTOCOL` | `openai` | `openai` → `/chat/completions`；`anthropic` → `/messages` |
| `LLM_MODEL` | `Memory-Model` | 默认模型名 |
| `LLM_MAX_TOKENS` | `32768` | 输出上限（`ingest-v2/llm.ts` 默认 8192） |
| `LLM_TIMEOUT_MS` | `1200000` | 20min，reasoning 模型预留 |
| `LLM_API_KEY` / `LLM_BASE_URL` | 空 | BYO 直连凭证；proxy 模式由 binding 提供 |
| `PORT` / `KNOWLEDGE_DATA_DIR` / `KNOWLEDGE_DB_PATH` / `KNOWLEDGE_PUBLIC_BASE_URL` | … | 服务与存储 |

### 2.3 LLM 调用链路

```text
POST /v3/wiki/ingest（routes/wiki.ts，wiki 有源文件才允许）
  → resolveLlmConfig(serviceId, llmBindingStore.get(serviceId), env 兜底)
      ├─ binding.mode=proxy → baseUrl = <proxy_base_url>/proxy/<serviceId>/v1（api_key 来自 binding）
      ├─ binding.mode=byo   → binding 自带端点
      └─ 无 binding：mode=proxy 时清空凭证 → ingest 大声失败（不静默直连）
  → 两阶段（OQ-4）：
      ① buildAnalysisSystemPrompt + buildAnalysisPrompt → 抽取计划
      ② buildSystemPrompt + buildGenerateFromAnalysisPrompt → FILE 块页面
     单阶段：buildSystemPrompt + buildGeneratePrompt → 直接 FILE 块
  → generateText(ai SDK)：openai → createOpenAI；anthropic → createAnthropic

wiki 就绪回调（callback.ts，TMC 触发）
  → generateWikiSummary：≤100 字中文摘要（createLlmClient，同一条配置链）
```

### 2.4 LLM Binding（按 instance 粒度路由）

- 路由：`/v3/internal/llm-binding/{set,status,list}`（`x-tdai-service-id` 头必填，internal 网络信任，无额外鉴权）
- `set` 幂等 upsert：`{mode: proxy|byo, proxy_base_url?, api_key?, enabled}`；`status`/`list` 永不回传明文 api_key。
- 用途：TMC 控制面 / 运维 curl 为每个租户把 wiki ingest 的 LLM 流量指到 context_proxy 或自建端点。

### 2.5 Proxy 注入面（Agent 可见，无 LLM）

- `KnowledgeToolsInjector` → `<knowledge_tools>` 只读查询工具（wiki 搜索 7 个 + code-graph 9 个）
- `knowledge/core-client.ts` → `POST /v3/knowledge/list {team_id}`（session_init prewarm 拉团队知识资产清单）
- `MemoryPanel` 侧：知识资产管理走 panel API（`panel/http/routes/knowledge/`）

## 3. 两侧对照速查

| 维度 | Skill | Knowledge |
|---|---|---|
| 进程 | memory-core 内核内 | MemoryKnowledge 独立服务（8421） |
| LLM 配置来源 | 内核 YAML 顶层 `llm:`（与 L1-L3 共用） | 环境变量 + 每 instance llm_binding |
| LLM 调用点 | 1 个：Skill Review Agent（工具循环，多轮） | 2 类：wiki ingest（单/两阶段）+ wiki 摘要 |
| 协议 | OpenAI 兼容（StandaloneLLMRunner） | openai / anthropic 双协议（ai SDK） |
| 无 LLM 的注入面 | `<available_skills>` / `<skill_tools>` | `<knowledge_tools>`（只读工具） |
| 失败策略 | LLM 未配置 → `LLM_UNAVAILABLE` 报错 | proxy 模式无 binding → 清空凭证大声失败 |
