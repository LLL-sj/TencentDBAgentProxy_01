# 记忆与 Skill 统一分层方案（调研 + 新目标设计）

> 日期：2026-09-07
> 说明：本文把“当前机制”和“新目标设计”整理成统一模板。目标是让 chat/code 的同一层、以及 L2/Skill，都拥有相同的字段结构，只允许 value 不同。
> L0 的原始请求/响应抽取细节仍见 `memory-agent/L0_ROUTING_AND_EXTRACTION.md`。

---

## 0. 统一模型

每一层统一使用四个字段描述：

| 字段 | 含义 |
|---|---|
| 触发条件 | 什么语义下会执行这一层；同一层 chat/code 使用相同触发模型，只是数值/来源不同 |
| 输入 | 这一层把什么交给系统/LLM |
| 输出 | 这一层产出什么 |
| 输出限制 | 数量、大小、token、格式等限制 |

并且：

- chat 与 code 的对应层必须是同一套字段结构；
- 值可以有差异；
- L2 与 Skill 也应是同一套“多文件维护”结构；
- L3 统一拆成“总结部分 + 索引部分”。

---

## 1. 总体链路

### 1.1 chat

```text
L0 → L1(chat 三类原子记忆) → L2(scene_blocks/*.md) → L3(persona.md 总结 + 自动索引)
```

### 1.2 code

```text
L0 + L0.5(summary_tips) → L1(code 四类原子记忆) → L2(project/topics/*.md) → L3(总结 + 自动索引)
```

### 1.3 all

同一份 L0 同时跑 chat 与 code 两条链路。

### 1.4 目标形态：L3 统一为“总结 + 索引”

新方案建议：

| 部分 | 谁来维护 | 更新时机 |
|---|---|---|
| L3 索引部分 | 工程代码 | L2 文件每次变化后自动扫描重建 |
| L3 总结部分 | LLM，用户也可手工编辑 | L2 发生足够多/足够重要的变化后触发更新 |

chat 当前 `persona.md` 更接近“总结部分”，还缺少自动索引；code 当前 `project/MEMORY.md` 更接近“索引部分”，还缺少 LLM 总结部分。目标是把两者都补成一致的两段式结构。

---

## 2. L0

### 触发条件

真实主对话每完成一轮，就把这一轮写入原始库；不调 LLM，不做总结。

### 输入

真实 User 文本、Agent 最终文本回复、身份与归属信息。

### 输出

`l0_conversations` 中的原始消息。

### 输出限制

不记录 tool_call/tool_result、内部请求、sidequery/fork、system 注入等。具体哪些 User/Assistant 是真实内容见 `L0_ROUTING_AND_EXTRACTION.md`。

---

## 3. L0.5

### 触发条件

Agent 完成一个“明确任务/阶段”，且该任务有可复用的步骤、产物、经验、注意事项或用户反馈时，主动提交 summary_tips；系统在合适时机提醒，不是每轮自动生成。

当前提醒细节：

- 新任务/阶段的第一条用户消息提醒一次；
- 用户新一轮消息出现时，上一轮 Agent 有文本回复累计 2 次后提醒；
- 上一轮 Agent 是纯文本最终答复、没有工具调用累计 2 次后提醒；
- 距上次提醒超过 480 秒且本阶段有新的文本答复轮次时提醒；
- 两次提醒至少间隔 600 秒；
- 同一 task 最多提醒 50 次；
- 阶段超过 7200 秒不活跃会重置；
- 出现 `<summary>...</summary>` 压缩交接块时立即提醒并重置。

### 输入

Agent 提交 `summary`、`steps`、`artifacts`、`tags`；系统附带 team/user/agent/session/task 和 L0 时间范围/引用。

### 输出

一条 `summary_tips` pending 记录。

### 输出限制

- 不是每轮自动产生；
- 必须满足“完整任务 + 可复用价值”；
- 相同锚点 + 相同 summary 去重；
- L1 成功消费后变 `consumed`，L1 失败保持 pending；
- 只在 code/all 模式参与。

## 4. L1

L1 是“原子记忆层”。chat/code 使用相同触发模型、相同输入输出结构，只是原子记忆类型和具体 value 不同。

### 4.1 统一结构

| 字段 | 当前值 / 说明 |
|---|---|
| 触发条件 | 同一 session 的新 L0 攒够一定用户轮次，或空闲一定时间兜底，或新会话 warmup 提前触发 |
| 输入 | 本批新 L0 + 少量背景 L0 + 上一个情境名；code v2 额外包含 L0.5 tips |
| 输出 | LLM 返回 JSON：情境数组 + memories[] |
| 输出限制 | 单批 L0 数量、背景数量、单次记忆条数、格式必须可解析 |

### 4.2 当前数值与建议调整

| 项 | 当前值 | 建议 |
|---|---|---|
| 稳定触发 | 每 5 个用户轮次触发一次 | 保持 5 |
| 空闲兜底 | 240 秒 | 按你的要求可改 300 秒（5 分钟） |
| 新会话 warmup | 1 → 2 → 4 → 5 | 改成直接从 2 → 5，不再走 1 和 4 |
| 单批新 L0 上限 | 10 条 | 改 25 条；因为 5 轮可能包含多条 assistant/tool/tips，10 太窄 |
| 背景 L0 | 约 5 条 | 可保留 5 条 |
| 单次 L1 条数上限 | 20 条 | 若希望更精简可改 10 条；当前你的意见是 L1 最多 10 条 |
| 去重 | L1 先做原子去重，L2 再做文件级合并 | 两层去重都保留 |

### 4.3 chat L1 类型与含义

| 类型 | 含义 |
|---|---|
| `persona` | 用户稳定特征：身份、职业、偏好、技能、价值观、习惯 |
| `episodic` | 客观发生的事件、决策、计划、结果，尽量带时间 |
| `instruction` | 用户要求 AI 长期遵守的规则、格式偏好、语气控制 |

### 4.4 code L1 类型与含义

| 类型 | 含义 |
|---|---|
| `work_fact` | 项目事实、需求、决策、状态、风险、约束、实验结果 |
| `work_task` | 待办、下一步、owner、deadline、任务状态 |
| `work_method` | 可复用 SOP、判断逻辑、原则、禁忌、经验 |
| `work_artifact` | 文档、PR、Issue、Prompt、报告、代码等资产 |

### 4.5 输入中的“上一个情境名”

“上一个 scene_name / work scene_name” 不是文件，而是上次 L1 给本段对话取的情境标签。

它的作用是让下一次 L1 知道：

- 如果对话仍在同一任务/主题，就继续沿用同一个情境名；
- 如果明显切换任务/主题，就创建新情境名。

这样同一主题的 L1 不会被“按批次切割成互不相关的片段”。

### 4.6 JSON 格式如何保证

当前不是“硬 schema 保证”，而是“提示词要求 + 解析容错 + 修复”。具体手段：

1. 系统提示要求只返回一个 JSON 数组；
2. 解析时去掉 ` ```json ` 代码块标记；
3. 从输出中提取第一个 `[...]`；
4. 清洗 JSON 字符串中的非法控制字符；
5. `JSON.parse` 失败后做一次修复，例如修复非法 `priority`、去掉尾逗号；
6. 仍失败则记录日志并返回空结果，不阻断对话。

后续如果要更稳，可以改为使用“结构化输出 / JSON Schema 工具调用”，而不是依赖模型手写 JSON。

## 5. L2

L2 是“多文件沉淀层”。chat L2、code L2 使用同一套结构；Skill 也应复用同一套多文件维护结构。

### 5.1 统一结构

| 字段 | chat L2 | code L2 | Skill |
|---|---|---|---|
| 触发条件 | 有新的 L1 且满足 L1 后延迟/最小间隔/周期兜底 | 有新的 L1 且满足 packager 延迟/最小间隔/周期兜底 | 归档 buffer 达到工具调用数/体积阈值后评审 |
| 输入 | 当前 L3 相关部分 + 已有 L2 清单/摘要 + 新 L1 | 当前 L3 相关部分 + 已有 topic 清单/摘要 + 新 L1 | 相关 Skill 摘要/正文 + 归档对话 |
| 输出 | 多个 `scene_blocks/*.md` | 多个 `project/topics/*.md` | 多个 `SKILL.md` |
| 输出限制 | 文件数量、单文件大小/token、总 token 预算、合并规则 | 文件数量、单文件大小/token、总 token 预算、合并规则 | Skill 数量、单 SKILL.md 大小/token、总 token 预算、合并规则 |

### 5.2 L2 当前数值

| 项 | chat L2 / code v1 | code v2 L2 |
|---|---|---|
| L1 后触发 | 30 秒检查 | 30 秒检查 |
| 最小间隔 | 180 秒 | packager 实际要求 300 秒 |
| 最大兜底 | 600 秒 | 600 秒 |
| 不活跃停止 | 3 小时 | 3 小时 |
| 文件数量上限 | 15 | 15 |
| 单文件字符限制 | 约 1500 字符 | 约 4000 字符 |
| L3 索引输入 | 当前没有明确索引 | `project/MEMORY.md` 约 6000 字符 |
| 一次最多新增 | 1 个新场景 | 不明确，但默认 UPDATE/MERGE |

### 5.3 L2 的合并/删除到底是怎么执行的

这里必须写清楚：**L2 不是一次 LLM 输出一个 JSON，再由工程去改文件。**

当前代码里，L2 走的是“工具调用式多步 LLM 执行”：

1. 第一次调用不一定完成；
2. LLM 可以调用 `read` 读取已有文件；
3. 调用 `write` 整体重写文件；
4. 调用 `edit` 局部修改；
5. 合并时创建新文件，并把被合并旧文件写成 `[DELETED]`；
6. 工程代码再清理 `[DELETED]` 文件并重建索引。

所以它本质上是多次 LLM 调用/工具调用，不是一次性 JSON 输出。

如果实际使用的模型不支持工具调用，这套机制就无法可靠工作。这种情况下，新方案可退化为：

- 一次性把所有相关 L2/L3 全文（或预算内截断）给 LLM；
- LLM 返回一组“最终文件集合”或“每个文件的完整新内容”；
- 由工程代码校验后执行新增、修改、删除。

但当前系统更偏向前者。

### 5.4 L2 输入是否应该包含全部 L2/L3？

建议不要“无条件全量”，而是设计一个统一预算模型：

- L2/L3 总量本身有上限；
- 每层文件单文件有 token/字符上限；
- 每次 L2 维护给一个总 token 预算；
- 在预算内优先提供“L3 总结 + 相关 L2 文件全文”；
- 不够放时才退化为“L3 总结 + L2 清单摘要 + 命中文件全文”。

这样既能避免模型不知道历史，又不会因为文件太多把上下文撑爆。

## 6. L3

### 6.1 统一结构

| 字段 | 说明 |
|---|---|
| 索引部分 | 工程自动扫描 L2 生成；每次 L2 变化后重建 |
| 总结部分 | LLM 基于 L2 变化生成/更新；也可由用户手工编辑 |
| 触发条件 | 总结部分不应每次 L2 都重写，而应在 L2 发生足够多/足够重要的变化后触发 |

### 6.2 当前 chat L3

- 当前触发计数：自上次 L3 后新增 L1 达到 10 条；
- 当前输入：已有 persona + 变化的 scene_blocks 内容；
- 当前输出：`persona.md`，接近“总结部分”；
- 当前限制：chat persona 约 2000 字符内。

问题：触发条件看 L1 条数，但真正生成看 L2 文件变化。二者会不一致。

### 6.3 当前 code L3

- 当前触发：L2 topics 变化后工程自动重建；
- 当前输出：`project/MEMORY.md`，接近“索引部分”；
- 当前限制：索引约 6000 字符；
- 缺少由 LLM 维护的“团队/项目总结部分”。

### 6.4 目标形态

| 部分 | chat | code |
|---|---|---|
| 索引部分 | 后续可生成 scene 导航/索引 | `project/MEMORY.md` 自动重建 |
| 总结部分 | `persona.md` LLM 维护 | 新增一个项目/团队总结文件，LLM 维护 |
| 触发 | 以 L2 变化为准，而不是 L1 条数 | L2 变化到一定次数后触发总结更新 |

## 7. Skill

### 7.1 当前触发与流程

Proxy 每完成一轮真实主对话，把本轮增量发给 core；core 在同一 session/agent 的 buffer 累计，直到满足任一条件才归档：

- 累计 tool_call 达到 10 次；
- 或累计原始字节约 40KB；
- 或单次过大触发压缩/oversize。

归档后调用 Skill Review LLM 判断是否需要新增/修改 Skill。

### 7.2 当前输入

- 最近该 agent 的 5 个 skill 名称 + 描述；
- 本段归档对话 transcript；
- 工具：skill_list / skill_view / skill_create / skill_update / skill_patch / skill_files_write。

### 7.3 当前输出

- 调用工具创建/更新/打补丁 SKILL.md；
- 或输出 `Nothing to save.`。

### 7.4 当前限制

- 不能删除 Skill；
- 必须先查询已有 Skill；
- 最终输出必须是工具操作 + 一句总结，或 `Nothing to save.`；
- 有质量门禁、SKILL.md 模板、命名限制；
- 最大迭代 16 轮；
- 当前没有数量上限、没有强制合并、没有单文件 token 限制。

### 7.5 新方案：Skill 与 L2 使用同一套多文件结构

目标参数示例：

| 项 | 建议 value |
|---|---|
| Skill 总数上限 | 例如 10 个 |
| 同一类 Skill 只允许一个文件 | 必须 UPDATE/MERGE |
| 达到上限先合并 | 是 |
| 每个 SKILL.md token 上限 | 独立设置 |
| 每次评审总 token 预算 | 独立设置 |
| 输入相关 Skill 内容方式 | L3 总结 + Skill 清单摘要 + 相关 SKILL.md 全文/截断 |

具体数值不需要和 L2 完全一样，但字段结构应一致。

## 8. 新方案总结

### 8.1 每一层都写清楚四件事

```text
触发条件
输入
输出
输出限制
```

### 8.2 chat/code 同层同构

| 层 | 相同结构 | 可不同 value |
|---|---|---|
| L1 | 触发模型、输入输出结构、类型字段 | chat 三类 vs code 四类；L0 是否带 tips |
| L2 | 多文件维护、合并规则、文件数量/大小预算 | 文件路径、单文件长度、触发间隔 |
| L3 | 索引 + 总结两部分 | 具体文件与触发阈值 |

### 8.3 Skill 与 L2 同构

Skill 应复用 L2 的“多文件维护”结构，但拥有自己独立的：

- 归档触发阈值；
- 输入对话来源；
- 文件数量上限；
- 单文件大小/token 上限；
- 总 token 预算；
- 合并/删除规则。

### 8.4 需要进一步改的方向

1. L1 单批新 L0 从 10 改为 25；
2. L1 warmup 从 1→2→4→5 改为 2→5；
3. L3 触发不再看 L1 条数，改为看 L2 变化；
4. L2/Skill 都引入“文件数量 + 单文件 token + 总预算”限制；
5. L2/Skill 都明确“多步工具调用式文件操作”的执行方式；
6. L3 统一成“索引自动重建 + 总结由 LLM/用户维护”。
